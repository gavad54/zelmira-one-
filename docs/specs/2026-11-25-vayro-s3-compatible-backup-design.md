# طرح فنی پشتیبان‌گیری مستقل VAYRO با فضای ذخیره‌سازی سازگار با S3

- تاریخ: 2026-11-25
- وضعیت: طرح تأییدشده؛ آماده برنامه‌ریزی اجرا
- دامنه: پشتیبان‌گیری و بازیابی پایگاه داده VAYRO-CORE
- تصمیم مهم: تا پیش از تأیید هزینه توسط مالک، ایجاد حساب/باکت یا خرید سرویس انجام نمی‌شود.

## 1. هدف

ایجاد زنجیره‌ای مستقل، قابل ممیزی و قابل بازیابی برای نسخه‌های پشتیبان VAYRO-CORE؛ به‌گونه‌ای که خرابی یا حذف داده در محیط اصلی، نسخه پشتیبان را از بین نبرد. راهکار باید با API سازگار با S3 کار کند و به Cloudflare R2 وابسته نباشد.

## 2. گزینه اولیه ارائه‌دهنده

SakooCloud Object Storage به‌عنوان گزینه فنی اولیه برای ارزیابی انتخاب می‌شود، نه انتخاب تجاری قطعی.

اطلاعات فنی اعلام‌شده:
- S3 endpoint: `https://s3.abrstorage.ir`
- Region: `ir-thr-1`
- پشتیبانی از API سازگار با S3 و ابزارهایی مانند AWS CLI و boto3
- استفاده از آدرس‌دهی path-style
- باکت خصوصی و کلیدهای دسترسی مستقل برای هر باکت
- قابلیت Object Lock باید هنگام ساخت باکت انتخاب شود.

پیش از انتخاب نهایی، مالک باید قیمت نهایی، روش پرداخت قابل استفاده، محدودیت ترافیک، محل نگهداری داده، سیاست حذف/نگهداری، پشتیبانی و شرایط حساب را از ارائه‌دهنده بررسی کند. اعتبار هدیه یا دوره آزمایشی، تا زمان تأیید کتبی شمول آن برای Object Storage، رایگان بودن سرویس تلقی نمی‌شود.

## 3. معماری پیشنهادی

1. GitHub Actions طبق زمان‌بندی روزانه و با امکان اجرای دستی، job پشتیبان‌گیری را اجرا می‌کند.
2. اتصال به PostgreSQL فقط با Secret محافظت‌شده GitHub Environment انجام می‌شود.
3. خروجی پایگاه داده با ابزار سازگار با نسخه PostgreSQL به‌صورت custom-format تهیه می‌شود.
4. اطلاعات سراسری PostgreSQL موردنیاز بازیابی، از جمله roleها و grantها، جداگانه ثبت می‌شود؛ اسرار و داده‌های حساس نباید در log قرار گیرند.
5. فایل‌ها پیش از خروج از runner با age رمزگذاری می‌شوند.
6. برای هر فایل SHA-256 محاسبه و همراه metadata نسخه، زمان، commit و نسخه ابزار ثبت می‌شود.
7. فایل رمزگذاری‌شده به باکت خصوصی S3 بارگذاری می‌شود.
8. پس از بارگذاری، وجود شیء و اندازه آن از راه API بررسی می‌شود. موفقیت upload به‌تنهایی معادل موفقیت بازیابی نیست.
9. بازیابی فقط در پایگاه داده آزمایشی و جدا از production انجام می‌شود.

## 4. تنظیمات S3

مقادیر اولیه برای محیط آزمایش:
- Endpoint: `https://s3.abrstorage.ir`
- Region: `ir-thr-1`
- Addressing style: `path`
- Bucket: نامی اختصاصی و غیرعمومی
- ACL و دسترسی عمومی: غیرفعال
- دسترسی کلید: حداقل مجوز لازم برای فهرست‌کردن/نوشتن/خواندن اشیای همان باکت

نام‌گذاری متغیرها باید عمومی و مستقل از ارائه‌دهنده باشد؛ برای مثال:
- Secret: `VAYRO_BACKUP_DATABASE_URL`
- Secret: `VAYRO_S3_ACCESS_KEY_ID`
- Secret: `VAYRO_S3_SECRET_ACCESS_KEY`
- Secret در محیط restore: کلید خصوصی age
- Variable: `VAYRO_BACKUP_AGE_RECIPIENT`
- Variable: `VAYRO_S3_BUCKET`
- Variable: `VAYRO_S3_ENDPOINT`
- Variable: `VAYRO_S3_REGION`

کلید خصوصی رمزگشایی نباید در مخزن، فایل workflow، log یا پیام گفتگو قرار گیرد. کلید عمومی age برای رمزگذاری قابل نگهداری در Variable است. کلیدهای S3 باید جداگانه و با حداقل دسترسی ساخته شوند.

برای AWS CLI باید path-style به‌صورت صریح تنظیم و رفتار checksum با نسخه CLI و سرویس مقصد آزمایش شود؛ در صورت نیاز از تنظیمات `AWS_REQUEST_CHECKSUM_CALCULATION=when_required` و `AWS_RESPONSE_CHECKSUM_VALIDATION=when_required` استفاده شود.

## 5. نگهداری و محافظت

- باکت خصوصی و بدون دسترسی عمومی.
- رمزگذاری سمت runner پیش از upload؛ رمزگذاری سمت سرویس، در صورت ارائه، لایه مکمل است و جایگزین رمزگذاری سمت کلاینت نیست.
- پیشنهاد اولیه نگهداری: نسخه‌های روزانه 30 روز و نسخه‌های ماهانه 12 ماه؛ مدت نهایی باید با هزینه و نیاز عملیاتی تأیید شود.
- Versioning و Object Lock فقط پس از بررسی هزینه، پشتیبانی واقعی و پیامدهای حذف/بازیابی فعال شوند.
- اعتبارنامه‌های backup و restore از هم جدا باشند؛ job روزانه نباید مجوز حذف نسخه‌های قبلی یا تغییر تنظیمات باکت داشته باشد.
- هشدار شکست job، کمبود فضای ذخیره‌سازی، نبود نسخه جدید و شکست restore باید به مالک گزارش شود.

## 6. آزمون بازیابی و معیار پذیرش

این موارد شرط اعلام آمادگی عملیاتی هستند:
1. یک نسخه پشتیبان رمزگذاری‌شده در باکت مستقل بارگذاری شود.
2. SHA-256 فایل دانلودشده با مقدار ثبت‌شده یکسان باشد.
3. رمزگشایی با کلید restore مجاز و خارج از مخزن انجام شود.
4. پایگاه داده در محیط آزمایشی مجزا بازیابی شود.
5. نسخه PostgreSQL، extensionها، schema، جدول‌ها، indexها، constraintها، roleها، grantها و سیاست‌های RLS بررسی شوند.
6. شمارش رکوردهای جداول مهم و آزمون‌های smoke/integration اجرا شوند.
7. زمان تهیه نسخه، حجم فایل، زمان بازیابی و نتیجه آزمون ثبت شود.
8. گزارش بازیابی توسط مالک بازبینی شود.

موفقیت backup بدون restore موفق، معیار پذیرش نیست. هیچ‌گاه آزمون restore روی پایگاه داده اصلی اجرا نمی‌شود.

## 7. تغییرات لازم در مخزن

Workflow فعلی `.github/workflows/vayro-db-backup.yml` به Cloudflare R2 وابسته است و endpoint را به دامنه R2 و region را به `auto` محدود می‌کند. برای پشتیبانی از ارائه‌دهنده S3 باید:
- اعتبارسنجی Cloudflare-specific حذف و اعتبارسنجی عمومی HTTPS/S3 جایگزین شود.
- نام متغیرها از R2 به S3 عمومی تغییر کند.
- endpoint، region و path-style قابل پیکربندی شوند.
- تست سازگاری checksum و upload/download اضافه شود.
- workflow مستقل restore به محیط آزمایشی ایجاد یا تکمیل شود.
- مستندات راه‌اندازی، چرخش کلیدها، بازیابی و واکنش به شکست به‌روزرسانی شوند.

این سند به‌تنهایی هیچ workflow یا تنظیم عملیاتی را تغییر نمی‌دهد.

## 8. محدودیت‌ها و موارد خارج از دامنه

- در این مرحله هیچ حساب یا باکتی ساخته نشده و هیچ هزینه‌ای ایجاد نشده است.
- هیچ Secret یا Variable در GitHub تنظیم نشده است.
- هیچ backup واقعی گرفته یا restore واقعی اجرا نشده است.
- هیچ تغییری در schema، migration، RLS، roleها یا داده‌های VAYRO-CORE مجاز یا انجام نشده است.
- انتخاب SakooCloud نهایی نیست؛ تأیید قیمت و شرایط توسط مالک لازم است.
- این طرح جایگزین نسخه پشتیبان مستقل از فایل‌ها/اسناد و مستندات زیرساختی خارج از PostgreSQL نیست.

## 9. مراحل بعدی

1. بازبینی طرح و تعیین سقف هزینه توسط مالک/سرپرست قانونی حساب پرداخت.
2. بررسی نهایی ارائه‌دهنده و تأیید شرایط و قیمت.
3. تهیه برنامه اجرایی و فهرست تغییرات workflow.
4. پیاده‌سازی در شاخه مستقل و اجرای آزمون‌های خودکار.
5. تنظیم Secretها توسط مالک در GitHub Environment؛ هیچ‌کدام در گفتگو ارسال نشوند.
6. اجرای backup آزمایشی و restore در محیط جدا.
7. فقط پس از شواهد موفق restore، درخواست مجوز جداگانه برای فعال‌سازی backup زمان‌بندی‌شده production.
