# ممیزی منبع و آمادگی چهار اپلیکیشن VAYRO

**تاریخ ممیزی:** 2026-11-19  
**نوع ممیزی:** خواندن مخازن و کد؛ بدون تغییر داده عملیاتی یا استقرار  
**وضعیت سند:** یافته‌های مستند منبع؛ نه گواهی انتشار

## 1. معماری مرجع

- VAYRO: مالک و حاکمیت اکوسیستم.
- DANA: مرکز فرماندهی و هماهنگی مجاز؛ نه اپ پنجم.
- چهار اپ مستقل: ARIA، ARIANA، LEADORA و ARMIN MARKET.
- هر اپ مالک کد، داده، هویت، مجوز، زیرساخت و چرخه انتشار خود است.
- ارتباط DANA فقط از API/event نسخه‌دار و هویت سرویس کم‌دسترسی مجاز است.
- ARIA فاقد حسابداری/ERP؛ ARIANA مالک حسابداری و ERP؛ LEADORA مالک فروش، توزیع، موجودی و عملیات؛ ARMIN MARKET مالک درخواست خرید و استعلام تأمین‌کننده است.

## 2. خلاصه وضعیت منبع

| اپ | منبع پیدا شده | شواهد موجود در کد | مانع اصلی |

## 3. یافته‌های تفصیلی

### 3.1 ARIA

**منبع:** `gavad54/aria-android`

شواهد خوانده‌شده:
- `README.md`، Blob: `fb3de308fd30b3605bd1325e0d3ae0e59826489e`
- `server.js`، Blob: `d3a342a2fcc972d0c1e19d9c47e0cd15fb0430dc`
- `package.json`، Blob: `cc182033bd1c31b4b74b9bda2a00c8c1481d83db`

**قابلیت‌های پیاده‌سازی‌شده در منبع:**
- Node.js API و رابط وب فارسی/RTL.
- ثبت‌نام و ورود با bcrypt، توکن کوتاه‌عمر امضاشده و endpoint اطلاعات حساب.
- ذخیره حساب، برنامه‌ها و صفحات در PostgreSQL؛ جداسازی داده برنامه/صفحه بر اساس user_id.
- محدودسازی نرخ درخواست API و اتصال اختیاری به API سازگار با OpenAI.
- تست‌های خودکار Node در CI.

**نواقص و موانع مستند:**
- README صریحاً تأیید ایمیل، بازیابی رمز، MFA، پایش سوءاستفاده، بازبینی حریم خصوصی/حقوقی، اعلان، صوت، هماهنگی agentها و انتشار Android را ناقص می‌داند.
- آرشیو کامل ARIA 32 در مخزن وارد نشده است؛ Gradle Wrapper، Android SDK و اثبات build/device موجود نیست.
- کلید ارائه‌دهنده هوش مصنوعی در مخزن وجود ندارد و نباید در کد یا گفتگو قرار گیرد؛ فعال‌سازی AI زنده نیازمند پیکربندی امن و تأیید هزینه است.

**تصمیم:** ساختار موجود حفظ شود. ابتدا ادغام منبع Android و آزمون مستقل وب/Android، سپس تکمیل امنیت حساب و قابلیت‌های اجتماعی/خدماتی. هیچ قابلیت حسابداری به ARIA منتقل نشود.

### 3.2 ARIANA

**وضعیت:** `SOURCE_NOT_LOCATED`.

- در مخازن قابل دسترس حساب متصل، مخزن معتبر ARIANA پیدا نشد.
- جست‌وجوی نام‌های ARIANA، ARIYANA و آریانا منبع قابل اتکایی برنگرداند.
- بنابراین هیچ ادعایی درباره کد، نسخه، پایگاه داده، آزمون یا درصد تکمیل فعلی ARIANA قابل اثبات نیست.

**تصمیم:** تا یافتن مخزن/آرشیو اصلی و تعیین محل داده، کدنویسی جایگزین یا مهاجرت انجام نشود. پس از دریافت منبع، ساختار قبلی حفظ و قابلیت‌ها با جریان‌های کاری نرم‌افزارهای حسابداری حرفه‌ای از جمله سپیدار مقایسه می‌شوند؛ کد، نشان و UI اختصاصی رقبا کپی نمی‌شود.

### 3.3 LEADORA

**منبع:** `gavad54/LEADORA`

شواهد خوانده‌شده:
- `README.md`، Blob: `aec6d5335cf889a75d77ee3dd4a61d98fc89854d`
- `app/main.py`، Blob: `2ce48e2860552a7d5c676625e0a14bedaf258e6e`
- `app/accounting.py`، Blob: `7a5250f77de62fa329aa2f9b402636f1976f4bbe`
- `app/distribution_erp.py`، Blob: `4c9313716555fe2fbe93c31248ce01ac0896c7b6`
- `app/participation.py`، Blob: `979002977d27f6a0fcd6f1b90a5445f5e7a5aac6`
- `tests/test_security_regression.py`، Blob: `afe120efee877b11a4535f2bced3babfe9744403`
- `tests/test_distribution_erp.py`، Blob: `d521945706976ea689878560dc543344164217f4`

**قابلیت‌ها و آزمون‌های موجود:**
- FastAPI و SQLite با tenant_id و آزمون‌های جداسازی کاربران/شرکت‌ها.
- محصولات، مشتریان، فاکتور، دریافت، هزینه، فرصت فروش، کمپین، lead discovery و workflow.
- worker مشتری‌یابی، history رویدادها، مجوز نرم‌افزار و حساب بانکی صرفاً دستی.
- ماژول توزیع شامل سفارش فروش، dispatch manifest، مرجوعی و گزارش‌های مالی؛ آزمون‌های tenant و جریان‌های توزیع در مخزن وجود دارند.
- تست‌های امنیتی شامل رد درخواست بدون توکن، هدرهای امنیتی، محدودیت ورودی و جداسازی tenant.

**تعارض مرزبندی معماری:**
- `app/main.py`، ماژول `app/accounting.py` و `app/distribution_erp.py` را به اپ متصل می‌کند.
- توضیح ماژول توزیع صراحتاً double-entry ledger و treasury را ذکر می‌کند و تست آن trial balance را بررسی می‌کند.
- این کد با مرز جدید مالکیت حسابداری در ARIANA و عدم مالکیت دفترکل در LEADORA تعارض دارد.

**اقدام لازم:** این قابلیت‌ها نباید حذف یا داده‌هایشان دور ریخته شود. باید به‌صورت دامنه‌ای ممیزی، داده و قراردادهای انتقالشان طراحی و در مسیر مستقل به ARIANA منتقل شوند؛ تا آن زمان قابلیت‌های مالی حساس LEADORA نباید به‌عنوان دفترکل نهایی یا جایگزین ARIANA معرفی شوند. این جداسازی نیازمند backup/restore و مهاجرت آزمایشی است.

**پشتیبان و بازیابی:**
- endpointهای پشتیبان JSON وجود دارند و داده‌های کسب‌وکار tenant را صادر می‌کنند.
- snapshot محلی JSON در پوشه سرور نوشته می‌شود؛ محتوای فایل در کد به‌صورت رمزنگاری‌شده ذخیره نمی‌شود.
- مسیر وضعیت storage فقط quick_check، شمار رکوردها و تنظیم مسیر را گزارش می‌کند؛ خود endpoint تضمین نمی‌کند که volume پایدار یا نسخه خارج از سرور وجود دارد.
- در کد بررسی‌شده endpoint بازیابی کامل (Restore) وجود نداشت.
- بنابراین Backup/Restore مستقل، رمزنگاری‌شده و آزموده‌شده **اثبات نشده است**.

**پرداخت:** اطلاعات حساب بانکی فقط دستی ثبت می‌شود؛ API اعلام می‌کند انتقال واقعی فعال نیست. این به معنای درگاه پرداخت یا تسویه واقعی نیست.

**ماژول مشارکت مالی:** `app/participation.py` در `app/main.py` به‌عنوان router فعال متصل است. این موضوع با درخواست قبلی برای خارج‌کردن «قرارداد مشارکت» از مسیر فعال نیازمند تعیین تکلیف در PR جداگانه است. در این ممیزی چیزی حذف یا غیرفعال نشده است.

## 4. DANA در VAYRO: وضعیت واقعی

شواهد خوانده‌شده از شاخه مهندسی VAYRO:
- `src/app/api/dana/generate/route.ts`، Blob: `c87cf618aa64427ea46e748c04766d426ae2ccc1`
- `src/app/api/dana/prompt-studio/route.ts`
- `src/app/dana/ai-workspace/page.tsx`

**موجود:**
- صفحه فضای کار دانا، درخواست متنی، بررسی نشست و دسترسی tenant، محدودسازی درخواست و تاریخچه تولیدات.
- prompt studio قالب متنی می‌سازد و در پاسخ خود اعلام می‌کند از AI provider استفاده نکرده و خروجی را ذخیره نمی‌کند.

**محدودیت قطعی در کد:**
- در مسیر تولید، `BILLING_LEDGER_READY = false` است و درخواست قبل از فراخوانی مدل با `billing_not_configured` متوقف می‌شود.
- این قفل عمدی است تا پیش از دفترکل اعتبار، هزینه API ایجاد نشود.
- در مسیرهای بررسی‌شده API اتصال و هماهنگی عملیاتی با ARIA، ARIANA، LEADORA یا ARMIN MARKET دیده نشد.

**نتیجه:** DANA فعلاً یک workspace و ابزار prompt در VAYRO است؛ مرکز فرماندهی عملیاتی چهار اپ هنوز اثبات نشده است. ساخت connectorها باید پس از تعریف API contract، هویت سرویس محدود، امضای پیام، idempotency، timeout/retry، audit و تست قطع DANA انجام شود.

## 6. اولویت مهندسی و معیار خروج

1. **ARIANA:** بازیابی منبع اصلی و تعیین نسخه/داده/مالکیت آن.
2. **LEADORA:** ممیزی دقیق ماژول‌های حسابداری و توزیع؛ جداسازی دامنه مالی از عملیات فروش بدون حذف داده؛ طراحی Backup رمزنگاری‌شده و Restore واقعی در محیط ایزوله.
3. **ARMIN MARKET:** تعریف Backend مستقل و تست end-to-end برای buyer request → supplier quotation → comparison؛ حذف یا برچسب‌گذاری دائمی داده‌های نمونه در build عملیاتی.
4. **ARIA:** واردکردن کامل منبع Android، تکمیل account security و اثبات build/device و backend.
5. **DANA:** API contracts نسخه‌دار، connectorهای مستقل و تست اینکه قطع DANA اپ‌ها را متوقف نکند.
6. **VAYRO Commercial:** تکمیل دفترکل append-only، idempotency، بازپرداخت، reconciliation و cost attribution در محیط آزمایشی؛ سپس بررسی حقوقی/ارائه‌دهنده و تأیید صریح مالک پیش از پرداخت واقعی.
7. **Release:** هر اپ به‌صورت جداگانه Backup/Restore، امنیت، CI، UAT، نسخه انتشار و مجوز مالک خود را لازم دارد.

## 7. محدودیت این ممیزی

این ممیزی از سورس‌های قابل دسترس GitHub و READMEها انجام شده است. دسترسی مستقیم به volumeهای Railway، داده‌های تولید، secrets، حساب‌های ارائه‌دهنده، device واقعی Android و فایل‌های خارج از مخازن در این مرحله انجام نشده است. بنابراین وضعیت زنده سرویس‌ها، تعداد کاربران، سلامت داده‌های عملیاتی، درآمد و Restore واقعی تأیید نشده‌اند.

**نتیجه نهایی:** ساختار چهار اپ مستقل و مرکز فرماندهی DANA از نظر معماری مستند شده؛ اما چهار اپ هنوز محصول تجاری کامل و آماده انتشار نیستند. بزرگ‌ترین موانع قابل اثبات: منبع مفقود ARIANA، حسابداری فعال داخل LEADORA برخلاف مرزبندی جدید، نبود Backup/Restore رمزنگاری‌شده LEADORA، نبود Backend عملیاتی ARMIN MARKET و نبود connectorهای عملیاتی DANA است.
